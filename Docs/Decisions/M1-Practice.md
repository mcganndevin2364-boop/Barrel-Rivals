# M1 practice decision record

Updated September 18, 2026. The initial 0.2.0/build 2 implementation and user-confirmed iPhone launch remain the baseline. Current source targets 0.3.0/build 3; its scene validation, 55/55 Editor tests and 5/5 Play Mode tests passed. Native compilation/signing and installation were verified; a targeted phone query confirmed 0.3.0/build 3. The new version has not yet been confirmed on the phone. [The polish decision record](M1-Practice-Polish.md) describes the current additions.

M1 continues from M0 commit `feabb99` in the same recovered project, on `codex/m1-skill-loop`. Foundation assets and its saved preview scene remain intact. `PracticeBuilder` owns `Assets/_Project/Generated/Practice`; it opens the foundation scene, saves a copy and changes that copy. Regeneration must not overwrite hand-authored production content.

The first connected increment is deliberately one barrel. Its pure C# state machine, trace scorer and path live in `com.barrelrivals.core`, compiled against .NET Standard 2.1/C# 9. `BarrelRivals.Practice` adapts Unity input, camera, HUD and audio. Existing `Runtime/Race` classes remain earlier scaffolding. This increment does not integrate their coin/reward logic, a rigged horse, full-course rules or multiplayer.

`PracticeRun.RulesVersion` identifies the local practice rules. Integer monotonic milliseconds drive explicit phase deadlines, and simulation time accumulates in microseconds across exact boundaries. The 4-second drawing window always contributes 1 second of simulated race time; early submission does not shorten it. Global Unity time scale does not control results. Identical accepted timestamped input produces the same result across tested render-step sizes. Input capture currently uses Unity processing time via [realtimeSinceStartupAsDouble](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Time-realtimeSinceStartupAsDouble.html), so physical input latency still needs measurement and future authority/timestamp contracts.

Launch cues use [AudioSource.PlayScheduled](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSource.PlayScheduled.html) on the DSP timeline. The first cue is scheduled 500 ms ahead. Visual cues derive from the practice clock; this is not a claim that audio output latency or audio/visual synchronization has been calibrated on phones. Generated sine tones avoid introducing unlicensed sound assets in the prototype.

Three local templates establish the drawing interaction: circle, triangle and square. The scorer uniformly normalizes translation/scale, preserves aspect/orientation, resamples a closed outline to 64 points, and searches cyclic starting points in both directions. Closure, extent, finite coordinates, duration, sample count and excess-length bounds reject unusable traces. A small geometry deadband limits resampling-phase bias. Speed contributes at most ten score points after a quality floor. This is a custom prototype grader, not a validated competitive recognizer or an anti-cheat system. Real-phone labelled traces, corners, scribbles, handedness and screen variation still require calibration.

One input owner is retained until release/cancel, even when its phase panel becomes transparent. Keeping the input objects active allows a held gesture to release after a deadline without becoming a fresh exit tap. A second pointer cannot release another pointer's hold. Focus loss/pause cancels offline practice and discards its result. In the original 0.2.0 build, Retry advanced the seed. In 0.3.0, Retry resets the model, owner, trace, audio and barrel presentation while preserving the exact seed; New Challenge advances the seed. The selected seed persists across restart. Future disconnect/reconnect rules require separate implementation.

Quality changes turn duration and radius; severe failure schedules a single knock at a defined point on the path. Barrel tilt and the immutable five-second penalty consume the same knock state. The finished `PracticeResult` describes one practice segment only. Full-course legal finish, DNF/tie/match result and settlement contracts belong to later increments. Nothing in this client-only scene grants trusted rewards, and its local seed must not be sent as a private competitive challenge manifest.

Visual review caught a missing CanvasRenderer on the custom uGUI drawing graphic. The component now requires that renderer, scene validation checks it, and Play Mode captures verify visible target/trace pixels. This demonstrates why passing rule/input tests alone is insufficient. Captures use the actual Unity camera and HUD after a frame warmup; appearance still needs physical-device review.

The user confirmed that 0.2.0 works on their iPhone and that the touch feel is good. Version 0.3.0 preserves all launch/drawing/exit thresholds, the automatic path and rules version 1. It adds a device-local shelf of up to 64 personal bests per exact seed/rules pair, penalized-time comparisons and one actionable coaching tip. Ties keep the prior best. A saved, bounded input replay must reproduce its recorded result before powering the explicitly labelled own-best ghost; this local consistency check is not server validation or an anti-cheat claim. Invalid or incompatible data cannot block practice, and failed record saves are surfaced in the HUD.

Sound, haptics and own-best ghost visibility have independent persisted controls. Procedural hoof/tack/dirt and grade feedback observe existing run state, use a fixed audio voice pool and own their generated clips. The original scheduled launch beeps respect the sound setting. Short iOS/Android feedback is optional and does not alter accepted input, race clocks or the camera. Original dirt textures, arena scenery and an articulated procedural horse improve presentation; the final rigged horse/rider remains an asset/integration decision, with no purchase made.

All tuning values are provisional and recorded in the M1 report. No paid resources, hosted services, store submissions or network middleware were introduced. M1N must prove private reveals, shared grading, accepted timing, independent windows and service failure behavior before adopting the proposed network/backend stack.
