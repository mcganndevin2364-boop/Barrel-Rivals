# Reins mechanics — implementation and acceptance contracts

Current design companion: gameplay revision 4 / engineering revision 5. This is the planned complete-stack integration of all ten requested mechanics. The 0.3.0 Classic checkpoint is existing work; Reins source, Unity scene, phone behavior, network service and economy must be reported separately as they are implemented and tested. Current source has shared mechanics, bounded horse parameters and local own-best playback. It has no Lab horse picker, learned behavior, bond/streak calculator UI, rival gap presentation or network/economy deployment. Mapping a mechanic below is not a completion claim.

Read [the Reins decision](../Decisions/Reins-Lab-Gameplay.md) first. Defaults pending user feedback: an additive opt-in Lab, and capped earned streak rewards without loss of existing winnings or premium insurance. All numeric values from the attachment remain provisional unless accepted into a versioned, tested configuration. A larger percentage is not a quality target.

## Ruleset and input contract

- **Classic:** existing `PracticeRun.RulesVersion == 1`; existing drawing records/replays remain exclusively Classic.
- **Reins:** `rulesetId = reins-lab-v1` plus schema version, rules/configuration hash, course ID/hash, horse/loadout ID/hash, footing map/round ID, input-mode ID and accepted event version. Separate local save namespace and replay decoder. Reject mismatches visibly; do not reinterpret Classic own-best data.
- **Simulation:** `ReinsRun` source uses 20 ms fixed steps in the shared .NET Standard 2.1 Core. Explicit finite/range limits, quantization/rounding and same-tick event ordering are rules. Rendering interpolation must not add/omit simulation time. Cross-runtime fixture equality remains a test obligation.
- **Input sample:** the target authority contract includes run/ruleset identity, sequence, capture timestamp, left/right tension, center cadence/Gate edges, held Wrap state, side-labelled Drive events and cancellation. Current local input frames are bounded simulation inputs, not a complete authenticated/timestamped network admission protocol. One center press supplies one cadence event; later eligible held Wrap is a distinct timeline state, not repeated cadence.
- **Two-thumb adapter:** current LEFT/RIGHT pads own rein drags; the active CENTER pad owns cadence/Gate presses and requests Wrap after a 300 ms hold near a barrel. One thumb holds the turning rein and the other taps/holds center. Both rein pulls brake and temporarily sacrifice center cadence/Wrap. Drive alternates side presses. Each pointer owns one pad until release/cancel. Center reach, hand changes and steering during Drive need device tests; three pads do not require three simultaneous touches. An exclusive two-zone tap/drag classifier is an unimplemented comparison option, not the current API.
- **Lifecycle:** a lost pointer cancels its held rein/wrap contribution. Offline interruption terminates or resets according to explicit Lab policy; online deadlines never pause or rewind. Menu touches cannot become gameplay taps. Accessibility presets have stable, declared rules; effects-only preferences never change performance.

Current geometric tuning uses a 0.42 m horse circle plus 0.40 m barrel circle (0.82 m contact radius), and a 1.0–1.2 m center-distance Kiss band. These are provisional prototype bounds, not verified real horse dimensions. Production clearance must be reconciled with authored art/collision hulls. Local own-best playback is present; the compatible rival-gap/network contract below is future work.

## Streak calculation proposal

The source's multiplier table and recursive example describe different models; recursively multiplying an accumulated pot also grows rapidly. Pending the user's preference, freeze base reward **B** when the eligible event begins and award B for each trusted win. Illustrative extra milestones are **+0.25B at win 3** and **+0.50B at win 5**, once each; cap extra rewards at **0.75B for that five-win cycle**, then begin a new cycle. Round integer currency once under the versioned policy. A loss resets future milestone progress, never previously awarded currency. A draw/void neither grants progress nor forfeits earned balance; final reset/pause semantics remain to be approved before economy activation.

These values are a tuning example, not production economy configuration. A local calculator/display is planned and must mint no coins. Later server settlement owns each base/bonus grant under a unique match/streak-cycle/milestone key. No premium insurance, staking of past winnings, cash-out transaction or IAP integration is part of R1/R2.
